How can one set of health data answer many different questions?

General practices, hospitals and community teams record different things in different systems. Data Vault 2.0 is one way to organise data for analysis so that new sources, corrections and reporting needs can be accommodated without repeatedly rebuilding everything.

Begin with a single laboratory result. The demonstrator gradually shows where its identity, relationships and value are stored, and how that same foundation supports different reports.

Lesson 1 of 7 · The problem

Why does healthcare need a flexible data layer?

Imagine an analyst is asked: How many patient encounters took place? Later, someone wants a patient’s sequence of results. A research team then wants a controlled extract containing measurements and their origins. These are different questions, often drawing on overlapping records.

Each source system was built to support its own work, not necessarily to answer every future question. Its identifiers, coding and data structures may differ from those of other systems. When new systems arrive or results are corrected, tightly coupled reporting pipelines may need changing.

The central idea

Keep a reusable, traceable record of what the sources supplied. Build different analytical views from that foundation, rather than imposing one permanent reporting shape on all incoming data.

A concrete healthcare example

Lesson 2 of 7 · Guided example

Meet the three building blocks

Data Vault separates identities, relationships and descriptions over time. These are called hubs, links and satellites. Follow the same HbA1c result through each step.

Before modelling

One row contains several different kinds of information

The GP feed combines who the measurement concerns, when it happened and the value recorded. This is convenient for the GP system. A reusable warehouse needs to distinguish the elements that have different patterns of change.

Building block 1 · Hub

A hub remembers which thing we are talking about

Hubs store business keys, meaning identifiers used to recognise a patient, encounter or observation. Each distinct key appears once within its defined hub. A hub normally also holds a technical key, when it was first loaded and where it came from.

HUB_PATIENTPAT-001HUB_ENCOUNTERGP-E01HUB_OBSERVATIONGP-O01
Notice

The hubs do not store the value 70. A corrected result should not require a new observation identity.

Building block 2 · Link

A link remembers how things relate

Links connect the identifiers held in hubs. The same patient can have many encounters, and an encounter can have several observations. The connections can be loaded without putting patient details into the observation hub.

PAT-001connected toGP-E01connected toGP-O01

Two link tables in this example: patient-to-encounter and encounter-to-observation. Real links normally store references to hub keys and their own load metadata.

Notice

A link is about the association, not about storing the clinical measurement value.

Building block 3 · Satellite

A satellite remembers what was said, and when

Satellites hold descriptive values and the history of changes for a hub or link. The observation satellite stores the local test code, the measured value, the unit, the clinical date and when the warehouse loaded that version.

ObservationResultClinical eventLoaded
GP-O0170 mmol/mol12 Jan 202613 Jan 2026
A later correction can append another row, preserving this original assertion.
Notice

Hub: GP-O01 stays the same. Satellite: a new version can be added when a reported value changes.

From building blocks to useful information

We can assemble different answers from the same underlying records

The data layer can join these keys, connections and values back together for particular needs. A service report counts encounters. A monitoring view selects suitable test results. A longitudinal view orders events for a patient.

Question AHow busy are services?

Count encounters by setting.

Question BWhat are the latest HbA1c results?

Apply agreed code mappings and select relevant values.

Question CWhat has changed over time?

Follow results and their successive source assertions.

Notice

Data Vault gives the reusable structure. It does not decide which results should count, whether different codes mean the same thing or who may see the output.

Step 1 of 5
Plain English first · Technical details optional

How the layers fit together

1. Source systems

Existing GP, hospital and community software produces records.

2. Raw Vault

Hubs, links and satellites organise source assertions and loading history.

3. Business Vault

Controlled rules interpret, select and connect records for reuse.

4. Analytical outputs

Different purpose-built datasets support reports and research.

These are architectural layers, not four separate mandatory technologies. A Business Vault can contain point-in-time or bridge structures and derived rules; an analytical output is often called a data mart or data product.

For readers who want the technical detail

In a production Data Vault, hubs generally contain a surrogate or hash key, a source-qualified business key, a load timestamp and record source. Links include participating hub keys, their own key and metadata. Satellites contain payloads, change-detection information and load metadata. Table grain, key policy and temporal semantics must be defined explicitly. A hash key is a repeatable technical identifier, not a patient matching algorithm or a privacy guarantee.

Corrective history is visible

With the late correction enabled, choose GP-O01 and compare February and August. The same source-qualified observation business key produces different results as known at those points in time, while the original version remains accessible.

Two different questions: “What was clinically effective in January?” and “What did the platform know in February?” must not be conflated. Bitemporal semantics require explicit rules, not just a load timestamp.

Illustrative SQL pattern

Conceptual query for the latest loaded version of each observation at a knowledge cut-off. Physical warehouse SQL, tie-breaking and satellite patterns will vary.

SELECT observation_bk, clinical_time, value, unit
FROM (
  SELECT o.observation_bk, s.clinical_time,
         s.value, s.unit,
         ROW_NUMBER() OVER (
           PARTITION BY s.observation_hk
           ORDER BY s.load_dts DESC, s.version_seq DESC
         ) AS rn
  FROM hub_observation o
  JOIN sat_observation_result s
    ON s.observation_hk = o.observation_hk
  WHERE s.load_dts <= :known_by
) versions
WHERE rn = 1;

The demo uses illustrative deterministic keys rather than real cryptographic hashes.

Data contracts around the Raw Vault

Semantic contract

Record code system, version, units, definition, allowed mappings and approved scope. A common warehouse key is not evidence that two clinical concepts match.

Quality contract

Assert completeness, validity, plausibility, timeliness and permitted use for each consumer. A preserved poor-quality assertion remains poor-quality data.

Governance contract

Define lawful purpose, access control, identity assurance, retention, erasure handling, clinical safety and approval of downstream transformations.

Lesson 7 of 7 · Understand the boundaries

What Data Vault can help with, and what it cannot do by itself

Data Vault is useful for preserving the lineage of analytical data and making extensions more manageable. But it is not a clinical record system, a terminology service, a master patient index or a guarantee that incoming data is suitable for a particular purpose.

Strong fit

Incremental integration and replayable history

Stable keys, independent satellites and provenance support extension, auditing and multiple purpose-specific marts. Source-specific attributes can evolve without forcing all consumers into one physical persistence schema.

Requires additional architecture

Semantics, identity and governed use

Record linkage, terminology, measurement comparability, data quality, authorisation, metadata management and permitted disclosure remain external or cross-cutting responsibilities.

Engineering trade-off

Join complexity and operational cost

Raw Vaults are not generally direct BI schemas. PITs, bridges and consumer marts reduce repeated joins, but introduce design, testing, refresh and infrastructure overhead.

Not the only valid pattern

Native repositories and federation

Data Vault is a pattern for historised analytical integration, not a clinical operational repository. It can coexist with FHIR, openEHR, preservation repositories, lakehouses and metadata-mediated federation rather than replacing them.

Keep this nearby

Plain-language glossary

You do not need to memorise these terms to follow the example. Expand any definition as needed.

Data warehouse

A data store organised to support reporting and analysis across one or more operational sources. It is distinct from the systems used to deliver care.

Data Vault 2.0

A wider method for developing adaptable analytical data platforms. Its familiar modelling pattern separates business identifiers (hubs), relationships (links) and descriptive history (satellites).

Business key and hash key

A business key is a source or governed identifier for something such as an encounter. A hash key is a technical value derived repeatably from a defined business key. Two different patient identifiers do not automatically become one person merely because hashes are used.

Hub, link and satellite

Hub: which thing? Link: how is it connected? Satellite: what is known or asserted about it, and when was that version loaded?

Raw Vault and Business Vault

The Raw Vault restructures and historises data received from sources. The Business Vault contains controlled derivations, reusable rules and query-assistance structures used when preparing specific analytical outputs.

Data mart or analytical endpoint

A dataset shaped to make a particular report, dashboard, study or analytical question straightforward. It is not necessarily the original format of the data.

Provenance, lineage and historisation

Provenance: where the data came from. Lineage: how it was transformed to reach an output. Historisation: keeping successive versions so earlier states can be examined.

Clinical event date versus warehouse load time

The clinical date describes when an event or measurement occurred. Warehouse load time says when its assertion reached the analytical platform. They answer different questions, particularly when a result arrives late or is corrected.

Code mapping and data quality

Mapping relates source codes to governed analytical concepts. Data quality refers to whether records are sufficiently complete, accurate, timely and appropriate for a particular use. Neither is assured simply by loading data into a vault.

Simulation checks

Checks test the internal consistency of this illustrative JavaScript dataset only. They are not conformance tests or assurance of a real deployment.

Method, scope and limitations

Method. The example uses synthetic pseudonymous identifiers, nine baseline GP observations and optional hospital/community observations. The model is a pedagogic schema demonstrating established Data Vault constructs and derives four browser-side outputs. Actions change in-memory state only; reloading resets the model.

Scope. The source records represent observations associated with encounters and organisations. No patient demographics, provider identities, sensitive attributes, diagnostic interpretations or real health records are loaded. The scenario assumes that a governed external process has supplied reconciled synthetic patient keys; it does not demonstrate patient matching.

Limitations. There is no physical database, parallel ingestion, incremental ETL, cryptographic key derivation, transactional constraint enforcement, consent management, data quality engine, semantic terminology service, genuine OMOP mapping or performance benchmark. The research endpoint is a staging extract, not a conformant OMOP Common Data Model. Demonstrated adaptability is not evidence of production effectiveness.
