01 · Executive judgement

Trustworthy healthcare reporting starts with a shared meaning.

Healthcare decision-makers rely on measures assembled from electronic patient records, administrative systems and laboratory services. Yet the same reporting label can conceal different event definitions, counting rules and local codes. The proposed capability makes those differences visible, governable and testable, without requiring every organisation to use the same software.

Design assurance: AmberInvestment concept, not a procurement specification

Recommendation: fund a bounded pilot of a shared reporting metadata capability. It should hold authoritative definitions for measures, record where the required data comes from, connect them to governed reference data, and retain evidence that each source-to-definition mapping is appropriate. The design should remain independent of the reporting, clinical and analytics products that use it.

What funding would buy: clearer accountability, reusable definitions and a way to assess whether reported figures remain comparable after system, coding or organisational changes. These are anticipated benefits to demonstrate, not savings already measured.

Assurance is Amber because the conceptual design is credible but its costs, benefits, ownership arrangements and operational effectiveness have not been established in a live service.

The immediate decisionAuthorise a scoped proof of value

Test the model with one real reporting measure and the systems that supply it.

The investment boundaryMetadata and assurance, not another data platform

Do not fund the copying of patient records, a replacement BI system or an unvalidated national roll-out.

The evidence to requireReconciliation and accountable sign-off

Show that the approved definition matches what the source systems actually record.

02 · The case for change

Why apparently straightforward reporting is difficult

A reporting measure often looks simple on a dashboard: a percentage, a count or a time interval. Behind that figure are decisions about who should be counted, which clinical or operational event starts and stops the clock, which organisational unit receives the activity, and how local system values are interpreted.

Those decisions may be scattered across database queries, spreadsheets, reporting specifications and the experience of individual analysts. Two teams can produce different answers without either calculation being obviously broken. A system replacement can also change a figure simply because the new system records an event differently. The problem is not just finding data. It is preserving the meaning of the question being answered.

Definition risk

What counts?

Before calculating a rate, someone must agree which attendances qualify, how exceptions are treated and exactly what “completed” means. A common label does not guarantee a common definition.

Source risk

Where is it recorded?

A patient administration system and a clinical system may both contain timestamps, but they may refer to different events. Selecting the wrong field can make a report consistent in form but misleading in substance.

Classification risk

How is it grouped?

Local service, outcome and organisation codes are not necessarily interchangeable. Their meaning may change over time. Reporting must know which code release and mapping were used.

Why this matters to funders: without a governed connection between the question, the source data and its classifications, effort tends to be repeated whenever an indicator is reused, a data source changes or a number is challenged. The scale of that effort and any resulting savings must be measured in a pilot; this page does not assert a quantified return.
03 · A worked reporting example

Follow one measure from a clinical question to a published figure

The demonstrator uses a synthetic emergency-department four-hour completion rate. It is deliberately simplified and is not an official NHS or HSE performance definition. Its purpose is to reveal the decisions needed to make any measure repeatable and auditable.

  1. 1

    Agree the meaning of the measure

    The reporting owner defines eligible attendances, which events mark arrival and completion, the 240-minute test, exclusions, reporting period and organisation attribution. These rules should remain understandable without reading a database query.

    Explore the canonical definition
  2. 2

    Describe the available source data

    The clinical event store has an arrival_utc field and a disposition_utc field. Another source may call its fields something else, or record a different event. Technical field descriptions alone do not establish that either source fulfils the agreed business rule.

    Inspect the source metadata
  3. 3

    Connect local codes to governed reporting categories

    The measure needs to know which local outcome codes qualify and which organisation should receive the activity. The mapping must use the appropriate reference-data release and effective dates, rather than assume that codes have fixed meanings forever.

    Examine reference-data mappings
  4. 4

    Record and test the connection

    A versioned mapping states which source fields fulfil which logical requirements, how values are transformed, who reviewed the equivalence, and what evidence supported approval. If the source event is ambiguous, the mapping is held for review.

    Validate a candidate mapping
  5. 5

    Keep the evidence when circumstances change

    When a field, source application or code list changes, the organisation can identify affected measures and assess whether historical and new results remain comparable. The metadata contract is preserved even if the software producing the report changes.

    See the change-impact view

04 · Public-service value

What becomes possible with a shared reporting metadata capability?

The aim is not to standardise every underlying clinical system. It is to standardise the description of reporting requirements and the evidence connecting those requirements to local implementations. That creates a common point of reference for analysts, service leaders, system suppliers and assurance teams.

Can we trust that two figures mean the same thing?Definitions and exceptions may be documented differently or buried in implementation logic.A common measure version, explicit mappings and recorded exceptions make comparability assessable, though not automatically proven.

What this is

A durable description of reporting meanings, their source dependencies and the approvals needed to trust them. The same model can support multiple reporting platforms and publication channels.

What this is not

It is not a replacement electronic patient record, a new national data warehouse, a mandatory reporting tool or a guarantee that existing source data are accurate. The architecture leaves operational data with their proper custodians.

Five terms used throughout this explainer

Measure: an agreed method for calculating a number, such as a rate, count or time interval. Indicator: a measure used to monitor performance, quality or a reporting commitment. Source asset: a system, dataset or field from which information may be obtained. Reference data: governed categories and identifiers used consistently in reporting. Mapping contract: a versioned record explaining how a source represents an agreed reporting requirement and what evidence supports that claim.

05 · Method and evidence

What the design is based on

This is a proposed design assembled from existing standards and earlier service-model work, not an official specification or an already implemented service. The distinction matters when considering investment: standards can reduce reinvention, but the organisation must still agree its definitions, ownership and assurance processes.

The model combines prior working analysis of federated metadata authority [SRC-01], recognised metadata and statistical concepts [WEB-01, WEB-02], and dataset/provenance standards [WEB-03, WEB-04]. These establish useful patterns, but none specifies the complete canonical model shown here. The associations, attributes and governance workflow are architectural proposals.

Fact

Standards describe relevant parts

ISO/IEC 11179-31 defines registration concepts for data elements and value domains. SDMX defines statistical structures and metadata. DCAT covers dataset discovery; PROV describes provenance. Each has a defined scope.

Analysis

A missing connection

Reporting meaning needs traceability from business definition to logical input to source field to transformation and reference-code conversion. A catalogue of tables or a list of KPIs alone cannot establish that connection.

06 · Canonical anatomy

Three authorities and a mapping contract

Think of the architecture as three connected records of truth. One explains the business question; one describes the available data; and one maintains the codes and classifications used to interpret it. A separate agreement, called a mapping contract, records why a particular source can answer the question.

Keeping these responsibilities separate is important. The clinical system remains responsible for what it recorded, the reporting owner decides how the measure is defined, and the reference-data owner governs classifications. The mapping documents how those distinct responsibilities meet.

The logical boundaries matter more than whether a future implementation uses one platform or several. Each object must have a persistent identity, a responsible steward and an explicit lifecycle.

07 · UML conceptual models

How the information fits together: the UML model

The diagrams provide a precise version of the same story for architects and suppliers. Each box represents a kind of information that needs managing, while a connecting line represents an association. The numbers indicate whether a relationship is one-to-one or one-to-many. Non-technical readers do not need to master UML to understand the proposal; the important point is that definitions, versions, sources and approvals remain connected.

What does “canonical metadata model” mean?

Canonical means a shared, agreed description that does not change merely because a supplier uses a different database or software product. Metadata means information describing the measure, the data it needs and the evidence for using those data. A canonical metadata model is therefore a common vocabulary and set of relationships, not a compulsory central storage system.

These are proposed UML class models, not a physical database schema or a normative interpretation of a specific standard. They show classes, attributes, associations and multiplicities. Select a class in either diagram to inspect its governance meaning.

09 · Reference data bridge

Why codes, classifications and dates matter

Reference data is the shared list of values that makes reporting categories consistent: for example, service types, organisations, attendance outcomes and reporting periods. Terminology governs the meaning of clinical codes and value sets. Neither should be silently rewritten in each reporting pipeline. Instead, the measure records the releases it relies on and how local codes are interpreted.

An organisation may reorganise its services while keeping historical reports. If figures are attributed using today's organisation hierarchy rather than the hierarchy valid when activity occurred, comparisons may become misleading. Versioned reference data and dated mappings make that policy choice explicit.

The reference-data component should register the canonical reporting scheme and its release, while preserving local values in source systems. A ValueMap records code conversions, effective dates, missing coverage and conditions. Clinical concepts can additionally reference terminology releases under their own authority [WEB-05].

11 · Lifecycle and decision trail

Who decides when a measure is ready for use?

A definition becomes trustworthy through decisions, not through the act of storing it. The reporting owner must approve the business meaning; source stewards confirm what operational fields actually represent; reference-data and terminology owners control the applicable classifications; and the responsible assurance function reviews the mappings and tests. The published measure then points to the versions that were approved.

The reporting owner approves the meaning; source stewards assert asset semantics; reference-data owners approve code and hierarchy releases; engineers establish executable mappings; independent reviewers challenge the evidence. Approval rights should be explicit rather than derived from possession of a metadata repository.

12 · Standards, policy and legal basis

How existing standards support the approach

Several established standards can contribute to a solution, but none covers the entire journey from a reporting question to an approved source mapping. This is why the proposal uses a neutral conceptual model and adapts standards for particular exchanges or artefacts, rather than selecting a single technology as the definition of the problem.

Standard or mechanismWhat it helps to representWhat it does not guarantee
ISO/IEC 11179-31 [WEB-01]Registered data elements, data element concepts, value domains and derivationsA turnkey reporting service or mappings to every source schema
SDMX 3.1 [WEB-02]Statistical concepts, dimensions, measures, DSDs, code lists, dataflows and reference metadataClinical equivalence of source events or conformance of calculations
W3C DCAT 3 [WEB-03]Descriptions of data assets, datasets, versions, distributions and data servicesField-level semantic mappings or approved indicator calculations
W3C PROV-O [WEB-04]Relationships among artefacts, activities, agents and derivationsValidation that the derivations were correct

Regulatory distinction: adoption of this particular canonical class model is not asserted to be a legal requirement. National reporting duties and EHDS dataset-catalogue obligations must be mapped to their actual legal instruments and competent authorities. The design helps preserve traceability but does not, by itself, establish regulatory compliance.

13 · Fairness, clarity and coherence

Meaning must be contestable by those responsible for the data

Reporting is consequential because performance figures influence planning, budgets, service scrutiny and public accountability. An apparent change in performance should not be confused with a change in how information was captured or classified. The governance model therefore gives people who understand the services and source systems the right to challenge an invalid mapping.

Report owners

Need a stable definition and comparable series, with visibility of exclusions, calculation changes and whether a historical result can still be interpreted under the same contract.

Source-data custodians

Must be able to correct catalogue records and challenge invalid equivalence claims. Ownership of an EPR or PAS does not imply authority to approve a national reporting measure.

Terminology and reference-data stewards

Need an explicit right to version classifications and flag breaking changes, while preserving their own release processes and external publisher constraints.

Patients, service users and public audiences

Are affected when misleading or incomparable statistics inform decisions. The design should preserve limitations, suppression rules and corrections rather than imply that all reported numbers are equally reliable.

The model deliberately distinguishes concept definition, asset description, mapping assertion and computed result. An ambiguous term such as “attendance completed” becomes a drafting risk if no event boundary or eligibility rule is recorded. An incomplete mapping remains a quality risk, not evidence that any particular source system is defective.

14 · Evidence, monitoring and viability

How to test whether the investment works

Funding should be conditional on a demonstration that the capability improves decisions, not merely on the delivery of a metadata catalogue. Technical completeness is a necessary starting point, but the stronger test is whether approved definitions can be traced into real data sources, reconciled against reported outputs and maintained through change.

Minimum feasibility

Can it be registered?

Identifiers resolve, required fields are populated, schema releases are known and versioned reference bindings can be stored.

Operational assurance

Can it be relied upon?

Event semantics, temporal rules, code conversion coverage, reconciliation and exception handling are verified using accountable reviewers.

Demonstrated effectiveness

Does it improve reporting?

Observe fewer unresolved definitions, faster source transitions, fewer unexplained breaks, and evidence of approved reuse across multiple products.

Track unresolved semantic equivalence claims, mappings awaiting source confirmation, orphaned source fields, reference-code coverage, overdue release impact reviews and reconciliations that fail agreed tolerances. A prototype can demonstrate the process, but it cannot prove production completeness, privacy compliance or that results are clinically meaningful.

16 · Investment and sponsorship

What should a funding decision actually authorise?

The right initial investment is a governed reporting metadata capability and a proof that it can improve one real reporting value chain. A new software licence or a large programme of catalogue population is not, by itself, evidence that reporting has become more reliable.

Capability to fund

Agree a common model, register measure definitions, describe source assets, govern reference-data bindings and record mapping approvals. Support controlled revisions, search, lineage, export and change notification. Establish named stewardship responsibilities alongside the technology.

Scope to keep outside the pilot

A national warehouse, wholesale replacement of analytics tools, central collection of patient records and an attempt to reconcile every existing KPI. Those may be separate programmes, but are not prerequisites to testing this design.

Gate 1 · Feasibility

Approve one measure and its authorities

Establish the definition, business owner, contributing systems and responsible data stewards. Record known uncertainties and a baseline of current reporting effort or disputes.

Continue only when: decision rights are accepted and the necessary source metadata can be obtained.

Gate 2 · Demonstration

Build and test the complete mapping

Document the logical inputs, relevant source fields, transformations, code mappings, effective dates and test evidence. Reconcile the candidate calculation with an agreed reference result.

Continue only when: source and reporting owners can explain and sign off the mapping, including its limitations.

Gate 3 · Controlled change

Prove that it survives a change

Introduce a different source schema or classification release. Demonstrate affected reporting products, approval requirements and whether comparability has been maintained.

Continue only when: the change is detected, reviewed and resolved with a traceable decision.

Gate 4 · Scale decision

Compare costs with measured value

Assess the time to register and validate a new measure, reuse of definitions, maintenance burden, quality of explanations and costs of keeping releases current.

Invest in wider adoption only when: demonstrated benefits and accountable operating arrangements justify the ongoing service.

What would the investment need to cover?

Costs will depend on the organisation's current assets and operating model. Budgeting should explicitly include subject-matter ownership and review, source discovery, terminology and reference-data stewardship, technical configuration or development, mapping and testing, training, and ongoing change management. No reliable cost or return-on-investment figure can be derived from this conceptual demonstrator.

17 · Recommended actions

Prove the model on one reporting value chain

A sensible first deployment is deliberately narrow. Pick one high-value measure with a clear sponsor, at least one source system and a meaningful reference-data dependency. Test whether the model clarifies decisions and identifies problems that would otherwise remain implicit. Use that evidence to decide whether the service warrants wider adoption.

  1. Agree canonical semantics. Register one indicator and its measure, population, calculation, time basis, grain and reporting dimensions, independent of all source platforms.
  2. Discover candidate assets. Catalogue all contributing source datasets, schema versions and essential field-level technical and semantic metadata.
  3. Establish the mapping register. Pin each logical-to-physical binding to a specific source release, with transformation rules, explicit null and time semantics, coverage and tests.
  4. Bring reference data into the dependency graph. Use governed codes and organisation hierarchies with release identifiers and effective-date logic, without transferring ownership to the reporting team.
  5. Execute a deliberate change. Simulate a source migration and a reference-data revision. Require a new mapping review and show whether historical results remain comparable.
  6. Only then choose implementation tooling. Evaluate systems against the required contracts, interoperability, change notifications, authorisation and independent export capabilities.
18 · Source register and limitations

Evidence and interpretive boundaries

These sources underpin the constituent standards and the distinction between reporting definitions, source descriptions, provenance and classifications. The integrated model and its approval workflow are a design proposal, not claims that a particular standard or regulation prescribes this exact solution.

SRC-01 · Earlier project design synthesis

European Healthcare Metadata, Terminology and Reference Data Service Model (23 October 2026), existing project working material. Used to preserve the distinction among semantic authorities and reporting stewardship. It is a proposal, not proof of an approved organisational mandate.

WEB-01 · ISO/IEC 11179-31:2023

Metadata registries, Part 31: Metamodel for data specification registration. Primary source for registered data elements, data element concepts, derivation rules and value domains.

WEB-02 · SDMX 3.1

SDMX Technical Specifications. Used for statistical concepts, dimensions, code lists, data structure definitions, reference metadata and exchange structures. SDMX 3.1 was released in May 2025.

WEB-03 · W3C DCAT Version 3

Data Catalog Vocabulary (DCAT), W3C Recommendation, 22 August 2024. Used to distinguish dataset/service catalogue metadata from the proposed field-level mapping register.

WEB-04 · W3C PROV-O

PROV Ontology. Used for representing lineage, artefacts and activities. It is not an assurance test.

WEB-05 · W3C SKOS

Simple Knowledge Organization System Reference. Used for classification schemes, concepts and mappings. More expressive operational constraints are required for time-bounded code transformations.

WEB-06 · HL7 FHIR R5 Measure

FHIR Measure resource. Used for structured computable quality-measure definitions and their distinction from evaluated outputs.

Limitations

The class model, synthetic source assets, code lists, sample mapping rules, approval logic and assurance ratings are illustrative designs. This page does not query source systems, load patient data, certify clinical accuracy, run SQL or reconcile real results. Browser-based approval and validation do not constitute authorised organisational decisions. The demonstration is self-contained and offline-readable, while optional external reference links require internet access.
