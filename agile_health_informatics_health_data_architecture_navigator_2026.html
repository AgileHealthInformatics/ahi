Executive judgement

The right answer is normally a composition of architectures, not a single platform.

The navigator takes a federated, lifecycle-aware position. Operational systems, clinical repositories, interoperability services, analytical models and archives solve different problems. They should be connected through shared identity, terminology, metadata, provenance and governance rather than collapsed into one universal model.

Do not make one representation do every job

A FHIR resource, an openEHR composition, an OMOP row, a Data Vault satellite and a dimensional fact table can all be legitimate representations of the same underlying event because they serve different purposes.

Centralise coordination selectively

Identity, terminology and shared definitions benefit from authoritative coordination. Clinical source data and contextual accountability often benefit from remaining closer to where they are created.

Preserve the transformations

Architecture is not only where data resides. Every mapping, derivation, profile, semantic layer and analytical model changes how the data can be interpreted. Those transitions require lineage and governance.

1Identify the authoritative operational source and the lifespan of the information.
2Decide where semantic meaning, identity and metadata are governed.

Centralisation and federation

Centralise the things that need one authoritative answer, not everything that happens to be data.

The distinction is architectural and governance-based rather than ideological. A health system may deliberately combine central coordination, local custody, selective replication and federated access.

A useful test

Ask what would be lost if the central service disappeared tomorrow. If an organisation could no longer state what its own data means because the semantic model exists only inside a supplier platform, the architecture has created semantic dependence even if every row of data remains exportable.

The safer target is portable data plus portable meaning: definitions, mappings, value sets, provenance, process state, business rules and model documentation should remain governable by the health system.

Federation without shared metadata creates fragmentation with extra steps. Centralisation without local accountability creates uniformity without trustworthy meaning.

Architecture anti-patterns

The failures usually come from asking a valid pattern to solve the wrong problem.

One model to rule them all

Universal canonicalisation

Forcing operational, exchange, analytical and archival needs into one model hides legitimate differences and pushes translation problems downstream.

One platform to do every job

Platform monoculture

A lakehouse, EHR, FHIR server or operational platform becomes the assumed answer to storage, integration, semantics, analytics and preservation simultaneously.

Rows are exportable

Semantic lock-in

Contracts guarantee data export while the models, mappings and object semantics needed to interpret those exports remain supplier-controlled.

Raw means safe

Data-lake literalism

Near-raw data is retained without the representation information, provenance and workflow context required to reconstruct its original meaning.

FHIR everywhere

Exchange model becomes persistence strategy

A strong interoperability representation is used as the answer to operational persistence, research, analytics and long-term preservation without separate architectural judgement.

Visibility equals coordination

Shared-record aggregation

More records are brought together without resolving authority, workflow state, provenance or semantic differences among sources.

A dashboard needs a source

Analytics becomes operational truth

Curated warehouse or lakehouse outputs are allowed to drive live care processes without acknowledging latency, transformation and purpose-specific semantics.

The archive has all the files

Storage without preservation

Historical data survives technically but cannot be interpreted confidently because code systems, reference tables, authorship and original context have disappeared.

Source register

Evidence and conceptual basis.

The navigator combines the supplied Health Data Operability framework with authoritative architecture and standards sources. Pattern assessments are analytical judgements, not claims made by the cited organisations.

SRC-01 · Health Data Operability: From Data Exchange to Shared Understanding

Primary conceptual source. Used for the federated semantic architecture, distinction between centralising coordination and centralising clinical data, metadata independence, preservation, trust, process context and architecture anti-patterns.

SRC-02 · WHO/ITU draft Reference Architecture Guidance for Digital Public Infrastructure for Health

Used as a contemporary public-sector reference architecture source for modular, standards-based national health infrastructure, shared building blocks and architectural coherence. The WHO consultation opened 9 July 2026 and closed 6 September 2026; the guidance remains draft at the date of this navigator.

WEB-01 · openEHR Architecture Overview

Used for the characterisation of openEHR as a model-driven architecture separating domain semantics from software and using archetypes/templates with versioned EHR structures.

WEB-02 · HL7 FHIR Architecture Overview

Used to position FHIR principally as a healthcare interoperability and application architecture rather than as a universal persistence or analytical model.

WEB-03 · IHE IT Infrastructure Technical Framework, Cross-Enterprise Document Sharing

Used for the document repository/registry and federated document-sharing pattern.

WEB-04 · OHDSI OMOP Common Data Model

Used for the characterisation of OMOP as an open community standard for standardising observational data to support reliable analyses and network research.

WEB-05 · Zhamak Dehghani, Data Mesh Principles and Logical Architecture

Used for the four data-mesh principles: domain ownership, data as a product, self-serve platform and federated computational governance.

WEB-06 · Data Vault Alliance, Data Vault 2.0

Used for Data Vault 2.0 as a combined modelling, architecture and methodology approach focused on historised, extensible analytical integration.

WEB-07 · Lakehouse architecture literature and current platform documentation

Used for the general lakehouse pattern combining lake-style storage with warehouse-style data management and analytical capabilities.

Limitation. Architecture patterns overlap, and actual implementations vary substantially. Current-use and strategic-potential indicators are evidence-informed qualitative judgements for navigation, not measured market adoption. Legal, security, clinical-safety and jurisdiction-specific requirements must be assessed separately.
